## What it is

A single-page, bilingual (English / Hebrew, RTL) shop for **Shweet Brew**, a small Modiin-based maker of South African biltong, boerewors, drywors, the "Holy Land Jerky" range (beef + chicken), Shweet Brew Shots and sweet chilli sauce, delivered across Israel. **Orders are placed on the site and stored in Supabase**; customers have no accounts; WhatsApp is only a contact channel. Admin phone apps for orders and stock are next. See "Backend (Supabase)" and "Where things stand" below.

**Caleb** builds the site with us; the **business owner** is someone else (he gives the product, kosher, legal and delivery facts). Older notes below say "the owner" and mean Caleb. **The GitHub repository is public:** no keys, private links or personal details in committed files.

Caleb works in short, casual messages ("yo fella", "chop chop"), often several numbered requests at once, sometimes mid-task, and reviews in the browser on localhost. He likes to see **options as artifacts** (clickable prototype pages published with the Artifact tool) for bigger design changes, but when he names a reference (e.g. "use the neighbour-s login") just build it. He prefers **minimal UI**: less clutter, fewer small texts, one question per step, no decorative icons above titles, big inputs, bigger photos, clear labelling. Motion should feel interactive but **not overdone** (he had animations toned down twice). He decided to **keep the original dark "Braai Fire & Blue Star" look**. He doesn't want his own server: everything runs on Supabase (no Python/Docker). Commit or push only when he says so.

## Key shared code

- `config/products.ts` — product registry (variants, sizes, prices in ₪, spice 0–5, kosher, nutrition, image). Hebrew names via `getTranslatedProductName` / `getCategoryNameHebrew`.
- `config/deliveryZones.ts` — zones, fees, days, next-delivery-date logic (production day Wednesday 12:00). Hebrew area/town/day names live in `ZONES_HE` / `DAYS_HE` with helpers `zoneName`, `zoneCities`, `zoneDays`.
- `config/languages.ts` — UI translations. Many components also use an inline `L(en, he)` helper.
- `contexts/LanguageContext.tsx` — language read synchronously from `localStorage["shweet-brew-language"]`; `index.html` also sets `<html lang dir>` before first paint to avoid an English flash.
- `contexts/CartContext.tsx` — cart items keyed by id + size, plus the shared checkout details (`shippingDetails` = street, `city`, `apartment`, area, name, phone, email twice, notes) and the shared checkout state (`tried`, `touched`, `submitting`, `payMethod`, `placed`: one memory for the cart and the Order section, which also stops an order being sent twice from the two places).
- `lib/orders.ts` — `submitOrder()` calls the `place_order` database function and returns the real `SB-####` reference or a typed error (out of stock, below minimum, bad phone/email…). No WhatsApp anywhere in ordering.
- `lib/supabase.ts` (lazy-loaded client), `lib/catalog.ts` + `contexts/CatalogContext.tsx` (live products/prices/stock; use `useCatalog()` instead of importing `PRODUCTS` in components).
- `lib/shopFilter.ts` — `openShop(filter)` lets the hero open the products section on a range (groups `wors`, `extras`).
- `lib/smoothScroll.ts` — Lenis smooth wheel scrolling; `scrollToTarget()` for all in-page jumps (one continuous ease-in-out glide, 0.9–1.8s); `lockPageScroll()` while the cart / popups are open; scrollable boxes carry `data-lenis-prevent`.
- `lib/reveal.ts` — scroll reveal (IntersectionObserver). Revealed = `data-revealed` attribute (not a class: React re-renders rewrite `className`, which used to hide product cards after opening their size tray, most visibly after a hero-tile jump). Variants by `data-reveal`: heading, text, zoom, wipe, fade, default. Below-the-fold elements are tagged **by selector** in `AUTO_TARGETS` (components don't need attributes); the hero uses attributes in JSX. `revealInstantly()` shows everything on a menu jump's path so nothing replays.
- `lib/parallax.ts` — gentle hero parallax/fade while scrolling away.
- `lib/fire/gl.ts` — small WebGL2 helpers (programs, noise texture, background compile, sparks) shared by the background and the steel braai. No 3D library.
- `lib/images.ts` — self-hosted photo helpers (`productSrcSet`, `productThumb`).

## Backend (Supabase)

Added 2026-11-19. The website talks to Supabase directly with the public anon key; Row Level Security and database functions do the protecting, so there is no server of our own.

**Files**
- `.env` (git-ignored, template in `.env.example`) holds exactly four values from the owner: `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (public, used by the site), `SUPABASE_SECRET_KEY` and `SUPABASE_JWKS` (secret: admin scripts / admin app server side only, never `VITE_`). Keep it to these; don't add more config. Restart the dev server after editing `.env` (Vite doesn't pick it up live).
- `supabase/migrations/` — the schema as numbered steps, run in order (each file sets up the security rules for its own tables):
  `0001_foundation` (helpers, plus an index of all files) · `0002_users` · `0003_delivery_zones` · `0004_catalog` · `0005_orders` · `0006_stock` · `0007_order_workflow` · `0008_place_order` · `0009_admin_views` · `0010_realtime` · `0011_product_images` (public `product-images` storage bucket; only admins upload) · `0012_api_grants` (newer Supabase projects don't grant API roles table access automatically) · `0013_auth_email_check` (`email_has_account`) · `0014_orders_need_confirmed_email` (the order gate) · `0015_guest_checkout` (guests order without a code; replaces the 0014 gate) · `0016_guest_email_required` (a guest order without an email is refused with `INVALID_INPUT:email`) · `0017_phone_optional` (phone may be empty; the 5-in-10-minutes guard counts the email too). **Live project (2026-11-24):** 0015, 0016 and 0017 were run and checked; 0008 and 0014 were re-run with 0015 in one transaction (0014 had never been run although these notes said so, and running 0015 without checking broke ordering until that repair). 0013 is there (its table and function exist) and real orders, items, stock and status changes work, so the order-related ones are in place; **0009, 0011 and 0012 were not checked individually**. Before running or relying on a migration, check the live state first (e.g. `select to_regprocedure('public.place_order_core(jsonb)') is not null;`). **`0018` and `0019` are written but not run on live; new changes go in `0020_…`; never edit an applied file.** The owner runs them in the SQL editor (we have no DB password).
- `supabase/seed.sql` — generated from `config/products.ts` + `config/deliveryZones.ts` by `npx tsx scripts/generate-supabase-seed.ts`. Insert-only (`on conflict do nothing`), so re-running never overwrites admin edits. Stock starts NULL = not tracked.

**Tables**
- Users: `profiles` (1:1 with `auth.users`, created by a signup trigger; `role` customer/admin). Users can edit only their own name/phone/address/language columns, never `role`. First admin: Supabase → Authentication → Add user, then in the SQL editor `update public.profiles set role = 'admin' where email = '…';`. After that admins use `admin_set_role()`.
- Products + stock: `categories` → `products` (id = the variant id used by the site) → `product_sizes` (label, price, `stock` in packs; NULL = untracked). Every stock change, from any source, writes a `stock_movements` row via a trigger (reason: order / order_cancelled / order_restored / restock / adjustment / correction). Admin functions: `admin_adjust_stock(size_id, ±n, reason, note)`, `admin_set_stock(size_id, n|null, note)`. View `stock_overview` (with a `stock_state` of ok / low / out / untracked).
- Orders: `orders` (reference `SB-1001`…, status new → confirmed → preparing → ready_for_pickup / out_for_delivery → delivered, or cancelled; payment status; `source` website/whatsapp/phone/admin), `order_items` (name/price snapshots), `order_status_history` (trigger). Cancelling an order gives its stock back; reopening takes it again (fails if gone). View `order_overview` (adds `item_count`).
- `delivery_zones` holds fee (NULL = to arrange) and minimum order (₪80, Modiin 0). Delivery days and towns stay in `deliveryZones.ts`. **When a zone's fee or minimum changes, update both** (or regenerate the seed for new zones).

**`place_order(p_order jsonb)`** is the only way to create an order from the browser: it ignores browser prices, checks availability and stock (row locks, so two buyers can't take the last pack), applies the zone fee/minimum, takes stock and returns `{reference, subtotal, delivery_fee, total}`. Errors are `INVALID_INPUT:<field>`, `OUT_OF_STOCK:<id>:<size>:<left>`, `UNAVAILABLE:<id>:<size>`, `BELOW_MINIMUM:<min>`, `TOO_MANY_ORDERS` (more than 5 orders per phone or email in 10 min, or 10 guest orders per IP in an hour); `parseOrderError` in `lib/orders.ts` maps them and the cart shows them in both languages. Admins can call it with `source: 'whatsapp'` to log a phone/WhatsApp order (no minimum).

**Security summary**: everyone reads the catalogue; only admins write it. Guests can't read any orders; signed-in customers read only their own. Nobody inserts orders directly; guests order through `place_order` only (limits: 5 per phone or email per 10 min, 10 guest orders per IP per hour). Tested on PGlite (95 checks, `tools/supabase-standin/db-tests.mjs`; run it from that folder's own `node_modules`, see its README); on the live project, guest orders work end to end (test orders SB-1001 to SB-1005, all cancelled; the next real one is SB-1006). No sign-up or logged-in order has been tried on live by us.

**Realtime**: `orders`, `order_items`, `products`, `product_sizes` are in the `supabase_realtime` publication. The site refreshes the catalogue on product/stock changes (debounced 400ms); the admin app should subscribe to `orders` (RLS limits what each user receives).

**Order emails** (2026-11-23): `supabase/functions/order-emails/index.ts`, a Supabase Edge Function run by a Database Webhook on `orders` INSERT (header `x-webhook-secret`). It reads the items with the service key and sends, through the Resend API, a "New order" alert to `OWNER_EMAIL` (website orders only) and "We've got your order SB-…: awaiting confirmation" to the customer in the order's language, when the order is placed (whether or not they press I've paid). One file, no imports, so the owner can paste it into the dashboard editor; `handleRequest` is exported so `tools/supabase-standin/order-emails-local.mjs` runs it under Node (tsx) with a fake Resend that writes `outbox/*.html`. Proven with SB-1001 (with phone) and SB-1005 (no phone): webhook 200, emails accepted by Resend, and the owner confirmed SB-1005's alert reached both `OWNER_EMAIL` inboxes. `OWNER_EMAIL` is split on commas only. Replies: `net._http_response`, or Edge Functions → order-emails → Logs. To change the code: edit the file, paste it into Edge Functions → order-emails → Code, deploy, then check that a call without the secret still answers our own `bad or missing x-webhook-secret` (a different 401 means JWT verification came back on and emails silently stop). Possible next step the owner asked about: a WhatsApp alert to the owner (CallMeBot, free, or the official WhatsApp Cloud API) from the same function; not decided. ## The steel braai (2026-11-25)

How it got here: the owner picked "Into the fire" for the page, then the bushveld fire for the bottom, then asked for more realistic options (five, as an artifact). They answered with a Pexels photo (14823745) as a reference; the steel braai was designed after it and built. Then: "i want the background to fade into the picture, so that it looks like it was always a part". From four blends they asked for Fire sky and Smoke on the full page, made lighter, and chose **Fire sky**. Built and committed 2026-11-25.

- **What it is:** a scene rendered offline by our own path tracer (no Blender, nothing downloaded; none of the photo's pixels are used, its tags say pork and ours is beef only), kept as separate light pictures in `client/public/images/fire/`: `wide-…` and `phone-…` (551px and narrower) × `base` (the low sun), `fire` (firelight, with the coals' glow folded in), `shares` (how much of the firelight comes from each of the four fire lights, so it can flicker), `masks` (r in front of the flames, g scene or sky, b leaves, already softened), `tongs`, `tongs-mask`. Stored on a log scale: the numbers are in `SCENE` in `braai.ts`. No sky: the page's background is the sky.
- **Live parts:** `SCENE` draws the lit scene into a texture about 16 times a second; `LIVE` adds flames, smoke, hot air, leaves and tongs every frame. `flames.ts` is a small fluid simulation (two fires in one texture, drawn seven times along the trough), `embers.ts` the sparks. The flames are tuned to exactly the noise in `gl.ts` (`NOISE_GLSL` and `createNoiseTexture`, shared with `background.ts`): changing it makes them curl sideways.
- **The stills** `images/fire/wide.webp` and `phone.webp` are see-through snapshots of the live canvas (whole picture plus the 34% above it), taken from the real page by `temp/fire/stills-site.mjs`. Take them again whenever the scene, the grade or `EXT` changes.
- **To change the scene** you must render again (about 10 to 15 minutes a picture on this PC), from the git-ignored `temp/fire`: geometry `geo2.mjs` (far things from `geo.mjs`), materials and light `mk2.mjs` → `tr2.mjs`, cameras `shots2.mjs`, then `node render2.mjs steel bg 1 60 14`, `… steel fg 1 110 14`, the same for `steelP` (72), `node full/enc.mjs`, and copy `full/art/{wide,phone}-*.webp` over. Cameras in `braai.ts` must match `shots2.mjs`. Don't delete `temp/fire/out` or `art`.
- **Tests:** `temp/fire/site.mjs` opens the real page on :3000 in Chrome (sizes, Hebrew, breeze and click, rotation, reduced motion, no WebGL).
- **Speed:** 60–61fps at desktop and phone sizes on the owner's laptop (Intel UHD), live 0.6–1 s after coming near; about 4–6 ms of graphics time a frame (it was 12–13 before it was made lighter; `temp/fire/full/gpu.mjs` measures it with the driver's own timer). Readings swing with whatever else uses the graphics chip (the Claude app itself took 57% once). Not tried on a real phone, Safari or Firefox.
- The bushveld fire's shader and stills are saved in `temp/braai` (`bushveld-shader.ts`) and in git (595f118).
- Fixed on the way: the closed cart drawer's shadow darkened the page's edge (`.cart-drawer` now has it only when open).

## Gotchas learned the hard way

- **Manus leftovers**: `vite.config.ts` has Manus editor plugins. The runtime and jsx-loc plugins are restricted to the dev server (`apply: "serve"`); in production they added a ~360KB inline script. Don't re-enable them for builds.
- **Vite sometimes serves stale CSS** after many edits; if styles look missing, touch `index.css` or restart the dev server.
- **The preview pane often runs hidden**: then the page renders no frames, so requestAnimationFrame, CSS transitions, Lenis glides and IntersectionObserver callbacks don't progress. Verify motion with DOM/computed-style checks, or ask the owner to look. Prefer `setTimeout` over `requestAnimationFrame` for start-up work.
- **Lenis**: `scrollTo` is ignored while stopped (use `force: true`, call `lenis.start()` / `lenis.resize()` first); measure targets from `window.scrollY` and `document.documentElement.scrollHeight`, not Lenis's cached size.
- **Outside-click handlers** must use capture phase + `event.composedPath()`; buttons that remove themselves on click otherwise look like "outside" and close the cart.
- **Stacking**: product cards create stacking contexts (animations), so popups must render via `createPortal(…, document.body)`.
- **Flag emoji don't render on Windows** — use the SVGs in `Flags.tsx`.
- **Artifacts**: never name a top-level function or const `top`, `name`, `status`, etc. — they clash with `window` globals and silently stop the whole script. Artifact pages can't load remote images; publish photos as `files` (or copy them from an earlier artifact with `{artifact, path}`).
- Editing large chunks via heredoc Python in Git Bash can hit quoting errors (or hang on stdin); writing a `.mjs` script to the scratchpad and running it with node works reliably. Make it fail unless every replacement matches exactly once, and normalise CRLF first.
- **Driving the site or Supabase in the preview pane:** typing and coordinate clicks sometimes don't land. Set inputs with the native value setter + an `input` event, fire `focusout` for blur, `keydown` Enter to pick a delivery area, and click by `ref`. If a drawer looks half open, call `document.getAnimations().forEach(a => a.finish())` before calling it a bug.
- **Putting code or SQL into the Supabase dashboard:** set it through `window.monaco.editor.getModels()[0].setValue()`, compare its SHA-256 with the local file (LF endings) *before* pressing Run or Deploy, and wrap migrations in `begin; … commit;`. The "destructive operations" warning appears for our functions (they contain `delete`/`truncate` on their own log/temp tables): read what triggers it and only confirm what the owner approved. The owner types every secret.
- **Stopping local test servers:** stopping the `npx tsx` task leaves its node child on :54400; check the port (and its command line) and stop only our own.
- **Phone on the same Wi-Fi:** Vite already listens on the network; Windows Firewall blocks it (Node.js has an inbound Block rule on Public networks). The owner was given the commands to open port 3000 on a private network; whether they ran them isn't known. The address changes with the network (`(Get-NetIPAddress -AddressFamily IPv4 -InterfaceAlias Wi-Fi).IPAddress`). Clipboard buttons need https.
- **Testing visuals:** screenshots from a hidden or contended browser mislead (1–2fps readings, half-faded text). Close and reopen the test browser, `bringToFront()`, and look at the pictures, don't trust numbers alone.
- **db-tests:** run `node tools/supabase-standin/db-tests.mjs .` from the project root. Every step "happens an hour later" so the 5-in-10-minutes guard doesn't trip; set `timePasses = false` around tests of the guard itself.
